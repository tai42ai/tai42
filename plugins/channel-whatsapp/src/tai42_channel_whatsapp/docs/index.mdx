title: WhatsApp channel (Meta Cloud API)
description: Configure the Meta Cloud API WhatsApp channel — the CHANNEL_WHATSAPP_ env group, the single webhook, rich messages, and the template window.
---

Bridge a WhatsApp number carried by the Meta Cloud API to an agent, or deliver
`ask` questions into it. Unlike Twilio, this channel sends interactive
controls, media, and pre-approved templates.

It holds **one pending question per `(phone_number_id, wa_id)` pair** so an inbound
reply correlates to the exact ask. When that ask is **withdrawn** — cancelled, or its
thread or person erased — the channel **releases that reservation immediately**, so the
next ask to the same `wa_id` is accepted at once instead of being refused until the held
reservation times out.

## Enable it

```yaml manifest.yml
channel_modules:
  - tai42_channel_whatsapp
```

## Configuration

The `CHANNEL_WHATSAPP_` env group. `CHANNEL_WHATSAPP_REDIS_URL` (and the
inherited connection-tuning fields) point the plugin-owned correlation store.

| Variable | Default | Effect |
| --- | --- | --- |
| `CHANNEL_WHATSAPP_ACCESS_TOKEN` | unset | Graph API bearer token for the send (one token serves many numbers). Secret. |
| `CHANNEL_WHATSAPP_APP_SECRET` | unset | Keys the `X-Hub-Signature-256` HMAC the inbound door checks over the raw body. Secret. |
| `CHANNEL_WHATSAPP_VERIFY_TOKEN` | unset | Shared secret echoed during Meta's GET webhook verification handshake. Secret. |
| `CHANNEL_WHATSAPP_DEFAULT_PHONE_NUMBER_ID` | unset | `phone_number_id` used as the sender for `ask` when none is routed. |
| `CHANNEL_WHATSAPP_ALLOWED_RECIPIENTS` | empty | Whitelist of `wa_id`s a caller-requested recipient must be on (`ask` only). Comma-separated or JSON list. |
| `CHANNEL_WHATSAPP_HTTP_TIMEOUT_SECONDS` | `30` | Timeout for the outbound send and the loopback answer forward. |
| `CHANNEL_WHATSAPP_DEDUPE_TTL` | `172800` | Seconds a handled `wamid` stays remembered (replay guard). |
| `CHANNEL_WHATSAPP_TEMPLATE_CONTACT_WINDOW_DAYS` | `30` | Rolling "seen within N days" window for template-send recipient policy; `0` disables known-contact tracking (allowlist-only). |
| `CHANNEL_WHATSAPP_REDIS_URL` | unset | Connection for the correlation store. |
| `CHANNEL_WHATSAPP_WABA_ID` | unset | WhatsApp Business Account id that owns Flows; required on the `form` paths. |
| `CHANNEL_WHATSAPP_FLOW_PRIVATE_KEY` | unset | Business RSA-2048 private key (PEM) the Flow data endpoint decrypts with; required only for a **reacting** form. Secret. |
| `CHANNEL_WHATSAPP_FLOW_PRIVATE_KEY_PASSPHRASE` | unset | Passphrase for an encrypted `CHANNEL_WHATSAPP_FLOW_PRIVATE_KEY` PEM. Secret. |
| `CHANNEL_WHATSAPP_FLOW_ENDPOINT_URI` | unset | Public URL of the Flow data endpoint, configured on a reacting Flow; required only for a reacting form. |

## Point the webhook at the deployment

Meta uses a **single** webhook endpoint for verification, inbound messages, and
delivery statuses (configured in the Meta App dashboard):

- Callback URL → `{public base URL}/api/channels/whatsapp/inbound`
- Verify token → the value of `CHANNEL_WHATSAPP_VERIFY_TOKEN`

On subscribe, Meta sends a `GET` with `hub.challenge`; the door echoes it only
when the verify token matches. Inbound messages and delivery statuses then arrive
as signed `POST`s on the same URL. A delivery status for a **bridge** message
updates its answer record (a `failed` ends it `failed`); a status for a **flow
send** (`notify_user`, which runs no bridge record) is instead posted as a
`delivery_receipt` event onto that send's monitoring trace — `failed` as an
`ERROR`. A status neither owns is acknowledged and ignored.

## Create a bridge route

`our_identity` is the number's **`phone_number_id`** (from the Meta dashboard),
not the display number:

```bash
tai conversations create chat-line \
  --door channel --target-name chat --execution-key chat-bot \
  --channel whatsapp --identity 109999888877776
```

## Rich messages

- **Interactive select asks** — when a `select` question is delivered, its
  options render as native WhatsApp controls: a short set becomes tappable reply
  buttons, a longer set a list message. Past WhatsApp's row cap, or when an
  option's text is too long for a button or row, the ask falls back to the
  numbered-text prompt so the person always sees every option in full. Either way
  the answer is the option text.
- **Rich notifications** — `notify_user` renders the full outbound vocabulary:
  **media** (image / document / video / audio each as its own native message; a
  link appended to the body), tappable **options** (`ReplyOption` → reply
  buttons or a list, sending an authored `id` on the wire when set; a lone
  `LinkOption` → a `cta_url` URL button), multi-section **lists** with per-row
  descriptions (`sections`), a media **header** + text **footer** on an
  interactive message, a shared **location**, an **ask-less form** (`schema`, an
  in-chat Flow), and out-of-window **templates** (`header_media` +
  `body_parameters` + quick-reply/url `buttons`). A choice surface, `schema`,
  and `template` are mutually exclusive on one send; media and location may
  combine with a choice surface. A channel that cannot render a given field never
  receives it (the send gates on the matching `supports_*` capability flag).

## Form asks

A `form` ask (an `ask` whose answer is a small JSON object) renders as an in-chat
**WhatsApp Flow**: the participant fills the fields and submits, and the completed
values return as the answer. A multi-page layout renders one screen per page, and
per-send prefill values and option lists open the form already filled in. A short
string `enum` renders a radio group (longer, a dropdown), an array of strings a
checkbox group, a constrained `format: date` a bounded calendar picker; a page's
display blocks and a review page render too, and a `visibleWhen` field is shown or
hidden client-side.

A form that **reacts while open** (its ask declares reaction triggers) publishes as
an endpoint-driven Flow whose controls call this plugin's encrypted Flow **data
endpoint** (`/api/channels/whatsapp/flow-data`); it needs the business key material
(`CHANNEL_WHATSAPP_FLOW_PRIVATE_KEY` + `CHANNEL_WHATSAPP_FLOW_ENDPOINT_URI`, and the
public key registered for the sending number) and refuses loudly without it. See the
plugin README for the provisioning steps.

Each schema property name may use any character, while a Flow component name must be
an identifier (`[A-Za-z_][A-Za-z0-9_]*`). The channel maps each property to a unique
identifier-safe component name for the Flow it publishes, and maps the submitted values
back to the original property names before returning the answer — so the answer keys are
always the schema's own property names, whatever characters they use.

The confirmation summary WhatsApp shows the participant after they submit lists each
field by its human-readable label (its schema `title`, else the property name), so the
summary reads in words rather than in the identifier-safe names; the channel maps those
labels back to the schema keys when it decodes the reply.

If the platform rejects a submitted answer (a value fails the answer schema at the
door), the **same form is re-sent** — same steps, same prefill, with the door's
reason shown above it — so the participant can correct and resubmit. This repeats
up to a fixed retry cap; past the cap the participant is told once that the form
could not be processed and the ask times out.

## Inbound entry parameters

When an inbound message enters the conversation **bridge** as a fresh turn (no
pending question to answer), the channel forwards opaque **entry parameters**
alongside the turn text, delivered verbatim to a `tool` target's payload under
`params`. The platform attaches no meaning and no trust; a consumer opts into the
keys it understands:

- `reply_id` (+ `reply_description` for a list row) — an interactive tap that is
  not an answer carries its question-bound wire id.
- `button_payload` — a **template quick-reply** tap (`button` message) carries the
  developer payload behind the visible button text.
- `context_message_id` — a message that quotes another carries the quoted `wamid`.
- `referral_source_url` / `referral_source_id` / `referral_source_type` /
  `referral_ctwa_clid` / `referral_headline` / `referral_body` — a click-to-WhatsApp
  or QR entry (`referral`) forwards its fields.
- `media_kind` / `media_id` / `media_mime_type` / `media_sha256` / `media_size` /
  `media_filename` / `media_voice` / `sticker_animated` — an inbound **media**
  message (image/document/audio/video/sticker) bridges with its caption as the
  turn text and its ingested identity in these params (see **Inbound media** below).
- `reaction_emoji` / `reaction_message_id` — an inbound emoji **reaction**.
- `contacts_count` / `contacts` — shared **contact** card(s).

Participant **media**, **location**, **contacts**, and **reactions** all bridge as
turns. An inbound **location** additionally lands as a typed `LocationElement` on
the turn (not a param).

## Inbound media

When a participant sends **media** (image / document / audio / video / sticker), the
channel looks up the Graph media object's short-lived lookaside url, streams the bytes,
and ingests them into the platform's served-media store. The bridged turn then carries
both a typed **`attachments`** entry — a `MediaItem` whose url is the served
`/api/interactions/media/<id>` reference — and the parity `media_*` params off that one
ingest (`media_id` is the served id, `media_mime_type` the sniffed-and-agreed type,
`media_sha256`/`media_size` the ingested content's digest and byte size, `media_filename`
the sanitised document name). The caption is the turn text, or a `[kind]` placeholder when
there is none.

If the bytes cannot be received, the participant is told once and the media is not bridged:

- **too large** — the object exceeds the operator's per-kind byte cap;
- **unsupported type** — the sniffed content is not on its kind's allowlist (or the declared
  and sniffed types disagree);
- **could not receive** — the media object has expired or is gone, or no media store is
  configured.

When a caption rode with a rejected media, the caption still bridges as a text-only turn so
the message is never lost. A **transient** fetch fault (a `5xx`, a timeout, or a torn read)
is not rejected: the webhook returns non-2xx, Meta redelivers, and the per-message dedupe
guards against a double turn.

Params ride only on the bridge path — a tap or quick-reply that **answers** a
pending question surfaces none (the answer path carries no params). Meta inbound
error notices (`errors[]`) are always logged at warning and never bridged; an
**unsupported-message-type** notice (`code 131051`) — participant content the
channel cannot receive — additionally sends the participant one generic
"unsupported content" reply and records a rejection event, while every other error
code stays log-only (an operator-facing vendor signal, not participant content). An
unhandled participant **content type** the plugin has no handler for likewise gets
the generic reply + event; a vendor **non-content** notification (`system` /
`request_welcome`) stays log-only. Each reply is sent once, deduped per message.

## The 24-hour window and templates

WhatsApp delivers freeform messages only inside a **24-hour service window**
opened by the client's last message. Outside it, a freeform reply is rejected
(synchronously, or later via a `failed` delivery-status webhook), and the record
ends `failed` rather than silently vanishing. Read failures with:

```bash
tai conversations failed
```

A **pre-approved template** is the one message delivered outside the window. Send
one with `notify_user`'s `template` input: a `name`, a `language`, an optional
`header_media` (image/video/document), positional `body_parameters` (body-text
fills), and per-button `buttons` (a quick-reply `payload` or a url suffix). Because
a template is billed and delivered cold, the
channel fences who may receive one: the recipient must be on
`CHANNEL_WHATSAPP_ALLOWED_RECIPIENTS`, or be a **known contact** — a number the
inbound webhook received a message from within
`CHANNEL_WHATSAPP_TEMPLATE_CONTACT_WINDOW_DAYS`. A template send to a cold,
unlisted number is refused loudly.

## Working-on-it signal

While a message runs its turn, the platform keeps WhatsApp's **typing indicator**
alive: it re-sends the indicator ahead of Meta's ~25 s dismissal window until the
reply is sent, so the participant sees it for the whole wait rather than only the
first few seconds. The refresh is bounded by the
`CONVERSATIONS_WORKING_SIGNAL_MAX_SECONDS` ceiling (`0` disables it entirely), with
`CONVERSATIONS_WORKING_SIGNAL_REFRESH_MARGIN_SECONDS` the margin it refreshes ahead
of each lapse. An inbound message is marked **read** the moment it is received,
independent of the indicator.
