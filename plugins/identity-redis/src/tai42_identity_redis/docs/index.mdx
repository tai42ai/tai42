title: Redis API-key identity
description: Configure the Redis-backed api-key identity provider — registration, provider selection, and the Redis the key records live in.
---

This is the default identity provider: it stores api-key hashes in Redis,
validates inbound tokens, and provisions and revokes keys. Access control is on
by default and the runtime refuses to boot with no identity provider registered,
so this plugin is the pairing every access-controlled install starts from.

## Register and select it

```yaml manifest.yml
lifecycle_modules:
  - tai42_identity_redis.redis_api_key_provider
```

The module registers itself as the `redis` provider at import.
`ACCESS_CONTROL_AUTH_PROVIDERS` (an ordered JSON list) names the chain the verifier
tries. Unset, the chain is every registered identity provider, sorted by name.

## Configuration

The provider owns its key store, so it reads its Redis connection and key namespace
from its own `TAI_IDENTITY_` env group. The access-control gate keeps its own Redis,
`ACCESS_CONTROL_REDIS_URL`, for policies, per-user live counters and the setup token.

| Variable | Default | Effect |
| --- | --- | --- |
| `ACCESS_CONTROL_ENABLE` | `true` | The access-control gate. Turn it off only for local, auth-free work. |
| `ACCESS_CONTROL_AUTH_PROVIDERS` | unset: every registered provider, sorted by name | Ordered provider chain the verifier tries. |
| `ACCESS_CONTROL_REDIS_URL` | unset | The gate's Redis: policies and per-user live counters. Falls back to the shared `TAI_DEFAULT_REDIS_URL`; with the gate on, one must be set. |
| `TAI_IDENTITY_REDIS_URL` | unset | Redis holding the key records. Falls back to the shared `TAI_DEFAULT_REDIS_URL`; with this provider loaded, one must be set. |
| `TAI_IDENTITY_KEY_PREFIX` | `ac:key:` | Namespace every key record carries (`<prefix><sha256 of the key>`). |
| `TAI_IDENTITY_REDIS_MAX_CONNECTIONS` | `10` | Connection pool size. |
| `TAI_IDENTITY_SOCKET_CONNECT_TIMEOUT` | `5` | Seconds to connect before the auth path fails; must be positive. |
| `TAI_IDENTITY_SOCKET_TIMEOUT` | `5` | Seconds per Redis read before the auth path fails. |
| `TAI_IDENTITY_RETRY_ON_TIMEOUT` | `true` | Retry a command that timed out. |
| `TAI_IDENTITY_RETRY_ATTEMPTS` | `0` | Retries after a first connection or timeout failure, with backoff. |
| `TAI_SETUP_TOKEN` | unset | Gate token for the one-shot `POST /api/setup` door that initializes the deployment. Unset, the platform auto-generates one and logs it once at startup; set it to pin a known value. |
| `TAI_SETUP_OPEN` | `false` | Drops the setup-token gate for local/dev. Leave off in any shared deployment. |

Any standard `redis-server` works — no RedisJSON module or `redis-stack` image is
required.

## Initialize the deployment

A fresh install has no principal and no key, and `tai keys create` authenticates
with one — so the deployment is initialized through the public, one-shot
`POST /api/setup` door. It creates the owner principal (an admin), mints the
owner's first key, and returns the raw `sk-…` key once. It is gated by a
boot-time token: set `TAI_SETUP_TOKEN`, or let the platform auto-generate one and
read it from the startup log (`setup token: …`). The door refuses with `409
Already initialized` once any principal exists.

```bash
tai setup --display-name alice --token -
```

The raw `sk-…` owner key is printed once — capture it then. Pass `-` to read the
setup token from stdin, keeping the secret off the command line. A keys-only
install (this provider with no accounts provider) sends no login; when an
accounts provider that attaches interactive logins is configured, the owner's
login is attached in the same call.

## Provision more keys

With the owner key in hand, mint further keys the normal way — the raw `sk-…`
value is printed once.

```bash
tai keys create --user ci --description 'CI key' --scope read
```
